Git 工作流：Feature Branch 最佳实践

2026-02-18 5 min read
Git协作

Feature Branch 工作流是中小团队最实用的 Git 模型：每个功能/修复在独立分支开发，通过 Pull Request 合并到主分支，保证 main 始终可部署。

分支命名规范

feature/add-user-auth
fix/login-redirect-loop
chore/update-dependencies
docs/api-readme

前缀表明类型，后面用 kebab-case 描述。一眼看出分支用途，便于自动化和清理。

标准流程

  1. 从最新的 main 拉分支：git checkout -b feature/xxx
  2. 小步提交，每个 commit 做一件事
  3. 推送并开 PR，填写 Summary 和 Test plan
  4. Code Review 通过后 squash merge 或 merge commit
  5. 删除已合并的远程分支

Commit Message

推荐 Conventional Commits：

feat: add particle background to homepage
fix: correct mobile nav toggle on iOS
docs: update README deployment section

类型 + 简短描述，必要时正文写「为什么」而非「做了什么」。

Rebase vs Merge

  • Rebase：保持线性历史，适合个人 feature 分支同步 main
  • Merge：保留分支拓扑，适合已 push 且他人基于其开发的分支
  • 黄金法则：不要 rebase 已共享的公共分支

PR 质量 checklist

  • Diff 控制在 400 行以内，大了就拆 PR
  • CI 全绿再请求 Review
  • 截图/录屏说明 UI 变更
  • 关联 Issue：Closes #123
好的 Git 工作流不是流程繁琐，而是让协作可预测、回滚可信赖、历史可阅读。
